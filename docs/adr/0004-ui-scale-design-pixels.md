# 界面尺寸用「设计像素 × 倍率」换算，不用 zoom

## Context

界面尺寸原本只跟字号配置的**文字**部分联动：`dshChat.fontSize` 改得动 `--font-size`，改不动
间距、图标、按钮盒、弹层宽高——字号调大后界面元素反倒显得挤。用户 2026-10-03 的口径是以
13px 为基准，按字号配置让界面尺寸一起等比缩放。

先要钉住一个事实：VS Code 给 webview 注入的 `--vscode-font-size` **恒为 13px**（它不随
`editor.fontSize`，后者只体现在 `--vscode-editor-font-size`）。所以配置为 `0`（auto）就是
基准字号本身，倍率恰好为 1——「auto 时与今天像素级一致」这条不变量由此成立，不是巧合。

改写的体量：`app.css` 里 790 个 px token、80 个不同取值（4/6/1/2/8/10px 六个值就占了过半），
其中 59 处是描边宽度。

## Decision

1. **倍率由 CSS 自己推导，只留一个真相**：`tokens.css` 的 `:root` 上
   `--ui-scale: calc(var(--font-size) / 13px)`，`--dp: calc(1px * var(--ui-scale))`；几何量一律
   写成 `calc(N * var(--dp))`（「N 个设计像素」）。JS 不重复算这个比值。
   挂在 `:root` 而不是 `.app`：图片浮层与右键菜单刻意挂在 `.app` 之外（全屏定位层），它们同样
   要用这些 token（`--radius-sm`、字号档位此前在那两个浮层里是拿不到的）。派生声明必须与字号
   覆盖点同一级——自定义属性的 `var()` 在**声明处**求值，所以字号覆盖也随之写在根元素上。
2. **倍率变量用 `@property` 注册成 `<number>`、初值 1**：写坏值时退回「不缩放」。实测未注册的
   自定义属性拿到坏值会让**整条声明**失效（`width` 掉回 `auto`），数百处里这等于布局全乱。
3. **四类量不换算**：描边宽度与下划线厚度（发丝线是一种约定，不是尺寸）、容器量
   （`100%`/`vw`/`cqw`/JS 量出来写回的尺寸）、纯容差（±1/±2px 的防抖与贴底判据）、时长。
   代码块字号反过来要跟倍率：`max(编辑器字号 × 倍率, 界面字号 − 1px)`——今天「代码比正文略大」
   的关系在任何倍率下都保住。
4. **与容器比较的阈值按倍率换算**（它们描述的是「内容需要多宽」：多窄撤掉轮次横条、多宽才够
   双栏 diff、多窄收成图标条）。容器查询用 `em` 表达——实测 `em` 在 `@container` 里相对**查询
   容器自身的字号**，于是阈值随倍率自动移动；`@media` 没这条路径（媒体查询的 `em` 固定按初始
   16px），所以轨迹面板那两条改成挂在面板根（`.trajectory-view`，因此它带上了
   `container-type: inline-size`）上的容器查询，写法统一为 `calc(N em / 13)`。必须留在 JS 里的
   三条（迷你模式、diff 双栏、轨迹检查器宽度）从视图模型的字号算倍率（`src/webview/uiScale.ts`），
   倍率一进 effect 依赖，字号改了立刻重判。

## Consequences

- **判据**：倍率 1（auto／13px）下改前改后像素级一致；8/16/20px 各人工看一遍。`app.css` 里
  几何属性上的裸 px 由断言看守，白名单只有描边、查询条件、容器量与 `--dp` 自身的定义行。
  落地的对拍：预览页 529 个元素的计算样式快照（位置/尺寸/字号/内外边距/间距/圆角/线宽）在
  倍率 1 下与改前**逐项一致**（0 处非噪声差异，噪声只有夹具里那条流式输出的运行中行；
  那次对拍在预览页补上 `scrollbar-color` 之前做的——补上之后预览的滚动条由自绘的 10px 变成
  与真机一致的 15px，属于预览保真度的修正，不是这次改写的几何差异）；
  8/13/20 三档实测：图标 24→14.77/24/36.92、胶囊高 18→27.69、轮次横条阈值 360→221/360/554、
  迷你模式阈值 220→135/220/338。
- **滚动条不在设计像素的账上**：用户实测「字号调到很大滚动条也不变宽」，查下来是 VS Code 的
  默认层给 `html` 写了 `scrollbar-color`，而它一旦存在，Chromium 就改用标准滚动条并**忽略
  `::-webkit-scrollbar*` 整组规则**（实测：同一条 `::-webkit-scrollbar{width:30px}` 在没有
  `scrollbar-color` 时是 30px，有了就变回 15px）。本仓历史上那组自绘滚动条（宽度、滑块、
  轨道、拐角、拉伸角）在真机上从来是死的，一并删掉；宽度与配色全交给 VS Code 的主题。
  连带记下一个**验证盲区**：预览页缺那条 `scrollbar-color`，webkit 路径在预览里是活的，
  于是「预览里看着生效、真机上不生效」这种差别预览永远照不出来——预览页现已复刻它，
  `scripts/styles.test.ts` 也钉住「不许再出现自绘滚动条规则 + 预览必须有 scrollbar-color」。
- 图标要单独说一句：SVG 的尺寸收不进 `width` 属性里的 `calc()`，所以 `icons.tsx` 的 `size`
  prop（连同品牌标、上下文圆环、spinner 三处手写 svg）改成 inline style 的 `dpLength(N)`。
  描边随之等比变粗——图标整体等比，不做 `non-scaling-stroke`。inline style 会压过样式表里
  针对 `svg` 的尺寸规则，所以这条改动的前提是「本仓没有这类规则」（已确认）。
- **「量出来的尺寸」是这个特性最容易漏的一半**：输入框的自适应高度、工具栏档位、气泡是否
  超行、路径是否被裁都是 JS 量出来的，字号一变就得重量（倍率进对应 effect 的依赖）。更要紧的
  是顺序：写 `--font-size` 的 App **必须用 `useInsertionEffect`**（早于所有 layout effect），
  因为 React 的 layout effect 是**子先父后**——写成 layout effect 的话，子组件在同一个提交里
  量到的还是上一档字号，量完设成写死的 px，父组件随后改字号不会让它重算。用户 2026-10-03 报的
  「刚调完字体输入框偏矮、敲一个字才正常」正是这个顺序问题（只把倍率加进依赖**不够**，实测过）。
  两处顺序不变量由 `scripts/styles.test.ts` 钉住。
- 代价是引入「设计像素」一个概念并改写全表；好处是它只有一个概念，且新增样式照着同样的写法
  就行。**没做**刻度 token 层（`--d-4`/`--d-6`…）：80 个取值里只有约 15 个进得了词表，其余仍要
  `calc`，「该用哪个」反倒多一道判断。
- **为什么不用 zoom**（一行就能「全场景等比」的诱惑）：实测 Chromium（webview 同引擎）里
  `zoom` 把坐标系劈成两半——`getBoundingClientRect()` 返回**缩放后**的值（倍率 2 时 440），
  而 `clientWidth`/`offsetWidth`/`scrollHeight`/computed style 仍是**未缩放**的布局值（220/50/
  2000）。本仓约十处混用两种空间（工具栏按实测宽度分配、迷你模式滞回、diff 双栏判定、
  滚动锚定与贴底补偿、轨迹检查器拖动、找词定位），放大后它们会静默错判：工具栏永远认为装不下、
  迷你模式永不触发、拖动宽度差一个倍率。此外 `--font-size` 已经在缩放文字，再叠一层 zoom 等于
  缩放两次，现有字号下发机制得反过来重做。
- **与官方 dsh web 的关系**：断点换算后，非默认字号下不再与官方的固定 px 口径逐像素对齐。这是
  本扩展自己的尺度特性，不涉及数据语义，故不影响「能力与数据语义与官方一致」这条约束。
- 轨迹面板的 `@media (max-width: 760px)` 原本是「官方 <=760px 同款行为」的镜子，改成容器查询后
  它跟着倍率走，与官方的固定线不再等价——这是刻意的（面板物理宽度不变、字号大了就该更早改抽屉）。
