**生命周期口径（用户 2026-09-14 明确）**：
- **外部 DSH**（`dshChat.url`）——完全不碰生命周期：不写租约、不写心跳、不杀进程；
- **本扩展启动的 DSH**——跟随扩展生命周期：最后一个使用它的扩展实例退出时彻底清理；
- **某个窗口禁用了扩展**——其它窗口不受影响，只是少了它那一份心跳；
- **所有窗口都禁用/崩溃**——下一次激活时按心跳判出"无人使用"并回收
  （没有进程在运行时不可能即时清理，这是机制边界，不是设计退让）。

**按有效配置分组**（用户口径 2026-09-14）：VS Code 设置是有作用域的，不同窗口的
`dshChat.url` / `command` 可能不同。会合信息按**有效配置**分目录
（`~/.dsh-chat/servers/<配置指纹>/`）：有效配置相同的窗口共用一个后台，不同的各管各的。
例：A、B 工作区各自写"内部 dsh"、全局用户设置是"外部 URL" → 只有 A/B 共用一个内部后台。

## 1. 需求（用户口径）与验收标准

| # | 需求 | 验收标准 |
|---|---|---|
| R1 | 多个 VS Code 窗口复用一个 DSH 后台 | 同时开 3 个窗口，机器上只有 **1 个** `dsh web` 进程（`node` 进程数可数） |
| R2 | **不管 `--port 0` 还是固定端口**都能复用 | 默认配置（`--port 0`）下 R1 成立；配置成固定端口时也成立 |
| R3 | **最后一个** VS Code 窗口关闭时才释放 DSH | 关掉最先启动后台的那个窗口，其余窗口**不受影响**；关掉最后一个窗口后进程消失 |
| R4 | 最后一个关闭的窗口**可能不是**最先创建后台的那个 | 即 R3 在「owner 先退、joiner 后退」的顺序下同样成立 |
| R5 | 崩溃遗留的内部后台要有处置 | 强杀 VS Code 后重开，残留 `dsh web` 被认出并清掉（现有能力），且**不得误杀**正在被其它窗口使用的后台 |

R2 是硬约束，也是本设计里唯一需要「绕一下」的地方（见 §2 事实 3）。

## 2. 实测事实（决定方案的五条，均已核实）

### 事实 1：启动令牌是**进程内内存随机值**，窗口之间拿不到

`dsh-client-connection/lib/index.js:227` 用 `WeakMap` → `:240-245` `randomBytes(32)` 生成，
只随公告行打印一次（`dsh-web-app/lib/index.js:203`）。**磁盘上没有任何地方存它**。

→ 结论：非 owner 窗口**无法**通过持久化手段拿到令牌。

### 事实 2：签名 cookie **跨重启有效**，但**绑定 host:port**

- 签名密钥落在 `$DSH_HOME/.credentials.yaml` 的 `client-connection/browser-session`
  记录里（`dsh-client-connection/lib/index.js:219,321-326`）→ 进程重启后仍在；
- 但 cookie 名 = `dsh-auth-` + `sha256(authority)`（`:280-281`），签名载荷里也带
  `authority` 并在每次请求比对（`:397,438`）→ **`:3080` 上换来的 cookie，在 `:54321` 上
  连名字都对不上，必然 401**；
- 环回地址的信任栅栏（`isLoopbackHostname`，`:120`）对端口不敏感，401 只来自这条绑定。

本仓库已有的探针 `scripts/cookieSurvivesRestart.ts` 正是钉这件事的：**同一固定端口**
起两次 `dsh web`，旧 cookie 仍然有效；换端口就会失效。

→ 结论：共享一个后台，**必须让所有窗口知道"当前是哪个 authority"**，并据此换取/复用 cookie。

### 事实 3：`dsh web` 是硬别名，**不接受** `--profile`

实测（本机 0.1.5-rc.1）：

```
$ dsh --profile web web --port 0 --no-open
error: web takes none of parent --profile, --from-default-profile, --patch, --dump-config, or --dump-default-config
```

`lib/bin.js:100-104` 里 `web` 子命令带 `allowUnknownOption + passThroughOptions`，
但父命令已经吃掉了 `--profile`，两者互斥。

→ 结论：**想用自定义 profile 就只能写 `dsh --profile <名字> …`**，`dsh web` 永远只启动内置
`web` profile（见 §7 之外的另一份回答）。

### 事实 4：宿主端**支持多客户端**，但**审批与提问是广播的**

- `dsh-api-gateway`：每个连接一个 `clientId` 存进 Map（`types/index.js:240-248`），
  事件广播给全部客户端（`:282-283`、`:336-337`），waterfall「第一个答复者胜」
  （`:352,364`）；WS 连接是一个 `Set`（`stream-server.js:11,37`）。
- 会话的 `cwd` 是**按会话由客户端提供**的（`SessionCreateRequest.workspaceId XOR cwd`，
  `dsh-api-session-controller/lib/types/types.d.ts:253-257`；`:572,579`），所以不同窗口用
  不同工作区目录是安全的；唯一的服务端全局兜底是它自己的 `process.cwd()`（`:2729`）。
- **代价**：审批弹窗与提问会被**广播到所有已连接窗口**，每个窗口都会显示同一个待办，
  谁先点谁生效。这是共享后台真实的行为变化，界面上需要能看出「这是别的窗口的会话」。

### 事实 5：DSH 没有单实例守卫，也没有端口/PID 文件

全包 grep `EADDRINUSE|already running|pidFile|singleInstance` 无命中；`withFileLock`
在 `finally` 里释放，**运行中的服务器不持有任何长期锁**（`dsh-atomic-write/lib/index.js:140-144`）。
两个 `--port 0` 服务器各拿一个空闲端口互不干扰；固定端口被占时第二个**启动失败**
（`dsh-host-webserver/lib/index.js:295-296`）。

→ 结论：「各窗口各起一个」当前是安全的（不是共享），本设计只是把它换成共享；
固定端口方案**必须**接受"端口被占就失败"。

## 3. 方案

### 3.1 一句话

**用一个「会合文件（rendezvous lease）」当唯一真相来源**：谁起后台谁把自己的
`baseUrl` + 启动令牌写进去；其它窗口读它、用令牌换 cookie、以**普通客户端**身份接上；
心跳与存活检测决定「什么时候该由谁接手、什么时候该杀」。

### 3.2 会合文件

复用现有的租约目录 `~/.dsh-chat/servers/`（`src/dsh/processRegistry.ts:124`），
把当前的「一个进程一张租约」升级成：

```jsonc
// ~/.dsh-chat/servers/server-<pid>.json
{
  "version": 2,
  "serverPid": 12345,                     // dsh web 进程（Windows 上是 cmd 外壳，/T 带走整棵树）
  "command": "dsh web --port 0 --no-open", // 谁起的、用什么命令起的（诊断 + 接管时复用）
  "baseUrl": "http://127.0.0.1:13579",     // 就绪后回填
  "token": "…",                            // 启动令牌（仅本用户可读，见 3.5）
  "startedAt": 1757000000000,
  "hosts": [                               // 正在使用这个后台的 VS Code 窗口
    { "pid": 4321, "workspace": "D:\\dev\\dsh-chat", "seenAt": 1757000005000 }
  ]
}
```

- **`hosts` 取代了原来的单个 `hostPid`**：它同时回答「还有谁在用」（R3/R4）与
  「谁已经死了」（R5）。`seenAt` 由心跳刷新（默认 5s，判定阈值 30s）。
- 旧格式（只有 `hostPid`）读到时按「单 host、无 token」处理并**就地升级**，
  不做版本迁移脚本（下一轮清理时自然收敛）。

### 3.3 三类判据（全部只认肯定证据，与 `isKillable` 同一纪律）

| 判据 | 定义 | 用途 |
|---|---|---|
| 进程活着 | `process.kill(pid, 0)` 成功或 EPERM | 基础 |
| 窗口活着 | `isProcessAlive(pid)` **且** `now - seenAt < 30s` | 决定「还有人在用」 |
| 可杀 | `!isProcessAlive(serverPid)` → 删租约；`isProcessAlive(serverPid)` 且无任何活着窗口且**命令行确认是 dsh** → `taskkill /T /F` | 清理 |

「拿不到命令行」时**不动手**（沿用 `processRegistry.isKillable` 的 `=== true` 纪律）——
那一态恰恰最无法排除「pid 已被回收」。

### 3.4 启动流程（每个窗口激活时）

```
install/activate
  → ① 取启动锁（见 3.6），读全部租约
  → ② 清理：把"hosts 全死"的租约删掉（进程也不在就顺带删）；此时**先不杀任何进程**
  → ③ 存在「服务器活着 + token 在」的租约？
        是 → 读 baseUrl/token，把自己追加进 hosts，释放锁，**以客户端身份接上**（不启动任何进程）
        否 → ④ 启动自己的 `dsh web`（命令来自配置），就绪后写租约（含 token 与 hosts=[我]），释放锁
  → ⑤ 释放锁之后，再对「确认是孤儿」的进程做 taskkill（这一步不能提前：见 §5 竞态 1）
  → ⑥ 起心跳定时器：每 5s 刷新自己那条 host 的 seenAt；顺带做一次自检（见 3.7）
```

### 3.5 令牌文件的权限

令牌等价于"在这个后台上的完整权限"。会合文件在**用户私有目录**
（`%USERPROFILE%\.dsh-chat\`，Windows 上默认已只对本人与管理员开放），并且我们
额外做两件事：

1. 写文件时尽量只给当前用户（Windows 下不强制改 ACL，仅文档说明该目录等价于凭据目录；
   已有 `.credentials.yaml` 同级的信任假设）；
2. **删除时机明确**：正常停止 / 判定孤儿 / 最后一个窗口退出时，连同租约一起删
   （`clearLease` 已在这个位置）。

风险与替代：不写令牌文件就得让用户在第二个窗口**手动粘贴令牌**（或固定端口 + 预存 cookie），
那与「自动复用」的需求直接冲突。**我建议写**，但这一条请你确认（§7 决策 B）。

### 3.6 启动锁（消解"同时启动两个后台"的竞态）

`~/.dsh-chat/servers/start.lock`：内容 `{pid, at}`，`wx` 独占创建。

- 拿到锁的窗口负责「扫描 → 决定起不起 → 写租约」，写完即释放；
- 拿不到锁的窗口**轮询等待**（≤ 启动超时）：等到的租约里已有活着服务器 → 直接接入；
- 锁持有者进程已死 / `at` 超过启动超时 → 视为残留锁，删除后重试（与
  `clearStaleDocumentLocks` 同一套判据：只在有肯定证据时删）。

### 3.7 心跳与自检（每个窗口每 5s）

1. 刷新自己那条 host 的 `seenAt`；
2. **连接健康**：`ensure()` 的现有连接若断了，重连；
3. **owner 缺席检测**：若自己不是 owner（没有服务器进程）且当前 `baseUrl` 不可达
   → 重读租约：
   - 有新租约（别的窗口已经接手）→ 换到新 `baseUrl`，用新 token 换 cookie，重连；
   - 没有 → 走 3.4 的 ④，**自己起一个**并接管（R4 的兜底：owner 崩了但 joiner 还活着）；
4. **最后一个退出者**：见 §4.1。

### 3.8 与「外部服务器」模式的关系

`dshChat.url` 非空 = 外部模式（现有语义不变）：

- **不参与**会合：不读不写租约、不做心跳、不启动任何进程，只连用户给的地址；
- 外部模式下 `dshChat.command` 与 `dshChat.autoStart` 不生效（已实现的配置注释口径）；
- 从"内部共享"切到"外部"时，按已实现的 `controller.reconnectServer()` 中止内部后台
  （连同租约与令牌文件一起清掉）。

## 4. 时序与崩溃处置

### 4.1 关闭顺序（R3 / R4）

**窗口退出钩子**（`deactivate`）：

```
若是外部模式 → 什么都不做
读租约，把自己从 hosts 里摘掉
├─ 还有别的活着窗口在使用同一后台 → 直接退出（后台留着）        ← R4：owner 先退也行
└─ 没有别的活窗口
   ├─ 我是 owner（租约里 serverPid 是我的子进程）→ taskkill /T /F + 删租约与令牌文件
   └─ 我不是 owner（owner 已先退，我被接手过）→ 我此时**就是** owner（见 3.7-3），同样杀掉
```

所以「谁是 owner」不是"最先启动的那个窗口"，而是**租约里当前写着 serverPid 的那条记录
的维护者**：owner 退出时若还有别人在，它**不杀进程**，只把自己从 hosts 摘掉；
下一位发现进程仍在就直接继续用（不需要任何"交接仪式"）——**这是 R4 最省事也最稳的解法**：
所有权不需要转移，因为"杀不杀"只取决于**还剩几个活窗口**。

### 4.2 崩溃矩阵

| 崩了什么 | 现象 | 处置 |
|---|---|---|
| 一个 joiner 窗口崩溃 | 它的 host 记录变陈旧 | 下一个窗口激活时删掉这条；进程不受影响 |
| **owner 窗口崩溃**，还有别的窗口 | 后台还活着、继续服务 | 活着的窗口在自检里发现"我连的后台还在，但我不是 owner 了"→ 步骤（3.7-3）把租约上的 owner 身份接管过来（改写 serverPid 归属标记），之后由它负责"最后关闭时杀掉" |
| **所有** VS Code 窗口崩溃 | 租约全陈、后台成孤儿 | 下次开窗 ① 扫描发现 hosts 全死 → 删租约；② 命令行确认 `dsh` → `taskkill`；③ 弹一条通知（已有文案 `Cleaned up {0} leftover dsh server process(es)`） |
| `dsh web` 进程自己崩了，窗口都活着 | 连接断开 | 各窗口自检发现 `baseUrl` 不可达 → 抢启动锁 → 第一个抢到的起新后台并写新租约（**端口可能变**）→ 其余窗口读到新租约并**换 baseUrl 重连**（这正是 §2 事实 3 要求的：新 authority 要换新 cookie，令牌就在新租约里） |
| 窗口崩溃后**重启**（VS Code 正常重载扩展） | 旧租约里还挂着自己的旧 hostPid | 启动时清理：`isProcessAlive(oldPid)` 为假 → 摘掉（新扩展宿主是**另一个 pid**，不能只按 workspace 匹配） |
| 启动锁持有者崩溃 | 锁文件残留 | 按 3.6 的判据清理；`at` 超过启动超时即视为残留 |

### 4.3 与现有 `cleanupResidualServers` 的关系

现有逻辑（`processRegistry.ts:448-480`）在激活期**无条件**清理孤儿。新流程要改成：

1. **先读后杀**：先判断有没有「活着的服务器 + 活着的窗口」，有就直接接入，**不进入清理**；
2. 清理只针对「确认是孤儿」的进程，且**推迟到启动锁释放之后**（避免杀掉另一个窗口
   正在等待就绪的后台——§5 竞态 1）；
3. 用户显式命令「DSH: 清理残留进程」保持原样（它本来就是手动动作）。

## 5. 与既有机制的冲突点（这些必须在实现时逐条处理）

**竞态 1：两个窗口同时激活。** 都在扫描时看到"没有服务器"，于是各起一个。
→ 由 3.6 的启动锁串行化；扫描与"写租约"必须在**同一把锁**内完成。

**竞态 2：窗口 A 起后台途中，窗口 B 判定它是孤儿。** B 看到租约里 `hostPid` 已死
（A 刚写租约就崩了）→ 杀。若 A 其实还活着只是慢，B 就会杀掉它正在等待的后台。
→ 清理由**心跳 + 启动锁**双保险：写租约与心跳都在锁内/定时刷新，阈值 30s 远大于启动 5s。

**冲突 3：`owned` 的语义。** 现在 `ServerInfo.owned` 表示"是本窗口拉起的"，
用来决定认证方式（自管走令牌、外部走 cookie/输入）。共享引入第三种：
**"是别的窗口拉起的，但我有它的令牌"** → 走"令牌换 cookie"，与自管同一条代码路径，
但**不能**在 `dispose()` 时杀掉它。→ `ServerInfo` 需要把「谁负责杀」独立成字段
（建议 `ownership: "self" | "peer" | "external"`），`dispose()` 只处理 `self`。

**冲突 4：`restart()`（命令「DSH: 重启服务器」）。** joiner 执行它会发生什么？
→ 需要决策（§7 决策 A）。

**冲突 5：审批广播（§2 事实 4）。** 共享后多窗口都会收到同一个审批/提问。
→ **不是缺陷，无需处理**（用户 2026-09-14 口径）：同一会话开在多个窗口时，
审批/提问同时出现在这些窗口里符合直觉——"两个窗口看的是同一个会话"本来就该如此，
先答者生效由网关保证。曾经计划做"标注来源/只让一个窗口可答"，已取消。

**冲突 6：每个窗口的"工作区"。** 会话的 `cwd` 是每会话由客户端给的（事实 4），
所以不同窗口不同工作区没有冲突；但**共享后台的"默认工作区"是 owner 的 cwd**
（`process.cwd()`），只有在客户端不传 `cwd/workspaceId` 时才会用到——现有代码
（`src/dsh/client.ts:342-351`：`workspaceId` 优先，否则发 `cwd`）始终传，所以
**无影响**，但要在注释里写清这条依赖（万一将来有人改成"不传 cwd 让服务端决定"，
共享后台就会按 owner 的目录建会话）。

**冲突 7：日志与诊断。** `dshChat.showDiagnostics` 现在报"是否由本扩展启动"。
→ 增加"共享后台：由 pid xxx 启动，当前 n 个窗口在使用"。

## 7. 已定的决策（2026-09-14 实施时）

## 8. 踩坑记录：为什么探针会"卡住"（2026-09-14）

这一轮在共享后台的端到端验证上反复遇到"命令不返回"，排查花了很久，根因值得记下来。

**三个坑叠在一起，任何一个单独出现都不会这么难查：**

1. **`build` 工具会一直等 stdout 管道 EOF。** 它捕获子进程输出，所以只要有**任何**
   继承了这条管道的进程还活着（哪怕它是被 spawn 的孙进程、且父进程早已退出），
   工具就不会返回。表现是"卡住"，实际是工具在等一个永远不会到来的 EOF。
   规避：长探针一律让子进程 `stdio: "ignore"` 或把输出写文件，然后用别的工具读文件。
2. **`process.kill(pid, 0)` 不能用来判断"我们自己 spawn 的子进程死没死"。**
   只要 Node 还握着那个子进程的句柄，进程被杀之后这个探测**照样返回成功**（僵尸态）。
   后果：断言假失败（"进程还在"），以及 `while (isProcessAlive(pid)) await …` 这种
   等待**永远不退出**——直接触发坑 1。
   规避：判"后台还在不在"用**端口/HTTP**（确定性事实），只在"要不要杀"的判据上
   用 `isProcessAlive`（那里保守一点是对的，见 `isKillable`）。
3. **观测代码自己不可信。** 中途加的 `say()` 日志（写 `.tmp/kill-probe.log`）实际
   一个字都没写进去，于是"没杀掉"的结论其实没有证据；同一时期 `fetch` 判断也给出过
   与 `netstat` 相反的结果。**先确认观测链路通了，再相信观测结果**——本仓库
   AGENTS.md 里那条「注入式回归验证先确认注入生效」是同一类教训。

**另外三条与沙箱/进程有关的澄清：**
- 沙箱**不是**这里的原因。`pwsh` 沙箱会让 `dsh` 写 `~/.dsh` 报 EPERM，但 `build`
  工具是宿主直连、不带沙箱。真正"卡住"的是**输出管道**，不是权限。
- 探针起真实 `dsh web` 时，**别在和用户共用的租约目录里做实验**（会互相接入/互相清理）。
  用 `DSH_CHAT_LEASE_DIR` 指到临时目录；子进程要**沿用**父进程传进来的值，
  否则父子各看各的目录（这个坑也踩过一次）。
- **不要用 `start /b cmd /c "…"` 起带引号的命令**（cmd 的引号剥离规则会把它拆坏，
  实测直接报"不是内部或外部命令"）。要后台跑就写个小 launcher（`.tmp/run-bg.mjs`：
  `detached + stdio ignore`）。

### 4. 清理路径的三个致命细节（"彻底清理"就靠它们）

这一轮真正难的不是共享，而是"最后一个窗口必须确实杀掉后台"。踩了三次，全部与
**进程生命周期**有关，逐条记下来：

1. **不能只杀租约里记的 pid。** Windows 上 `dsh web` 经 shell 启动，租约里那个是
   `cmd.exe` 外壳（实测 `CommandLine` 就是 `cmd.exe /d /s /c "dsh web …"`），真正的
   服务器是它的 node 子进程（实测：外壳 pid=164988，端口占用者 pid=165108）。
   外壳先死时（父进程被强杀），对旧 pid 调 `taskkill` 只会"找不到进程"。
   → 解法：`killLeasedServer` **先按 pid、再按端口**（`netstat -ano` 找出真正监听者）。
2. **`spawn` + `unref` 的 taskkill 会被调用方的 exit 带走。** 日志里能看到"已发起"，
   进程却纹丝不动（实测两次）。→ 解法：`spawnSync` 等它执行完——本地几十毫秒，
   窗口退出路径上"确定杀掉"远比"不阻塞"重要。
3. **清理不能写在会被 `process.exit` 掐断的异步尾巴里。** 探针的子进程在
   `dispose()` 之后立刻 `exit(0)`，异步清理还没发出去就没了。→ 解法：清理做成
   同步（见上），而不是"先发个 promise 再退出"。

### 5. "窗口被禁用"为什么必须按实例而不是按 pid 记心跳

一个 VS Code 窗口里所有扩展共享同一个扩展宿主进程 → 同一个窗口的多个对话面板
（本扩展有主侧栏/辅助侧栏/编辑区面板三种宿主）**pid 完全相同**。按 pid 记心跳时：

- 用户禁用了某个窗口的扩展，只要同窗口还有一个面板活着、或别的窗口用它自己的 pid
  续期，判据就永远认为"有人在用"——**禁用发现不了**；
- 反过来，本实例摘掉登记后，那条陈旧记录又会让判据**低估**"最后一个"，于是谁都
  不杀，留下孤儿。

所以每个扩展实例在激活时生成一个 `hostId`，各写一份 `hosts/<hostId>.json` 心跳；
判"还有人在用吗"**只看心跳文件**（`hasLiveHostFor`），pid 只用于"要不要杀"那一层。
两条断言分别钉住两个方向（见 `sharedLease.test.ts` 第 10 节）。
