## Lessons & Pitfalls 经验与坑

**查证官方 Web 端的高效路径**（本次审计据此完成）
先读 `dsh-client-ui-*/lib/types/**/*.d.ts` 契约（简短可读），再回 `lib/client.js`
grep 确认实现。直接读 632KB 的 `client.js` 会很痛苦。
官方包根：`%APPDATA%\npm\node_modules\@deepseek-ai\dsh\node_modules\@deepseek-ai\`。

**坑：死代码接上按钮才暴露**
`pickFiles` 在 HEAD 里从未被调用，其 `canSelectFiles: true, canSelectFolders: true`
在 Windows/Linux 上**只弹目录选择器、文件全被过滤**（`@types/vscode/index.d.ts:2063`
明文写了）。我把图片按钮改成通用入口接上它，用户立刻踩到。
→ 教训：把死代码接上线前，要逐项验证它依赖的外部契约。已加源码级不变量断言
（`scripts/attachments.test.ts` 扫 `showOpenDialog` 的两个标志）。

**坑：toast 通道只写不读**
`state.ts` 只把 `level === "error"` 存进 `state.error`，而 `state.error` **从未被渲染**
→ 复制成功、设置保存、图片被跳过等提示全部静默丢弃。是审计需求「必须出现提示」才发现的。
→ 教训：加提示类功能前先确认渲染路径存在。

**坑：`detail` 从右侧省略，后缀会被截掉**
读取行号最初拼进 `detail` 字符串，窄侧栏下正好被省略号截没（白做）。
改成单独一段不可压缩后缀（`.row-detail-suffix`）后，宁可截路径也保住行号。

**坑：flex 每行各自分配宽度**
思考档位定列最初用 `flex: 1 1 calc(100%/n - 6px)`，5 档时第二行两个被拉得比第一行三个宽
（103px vs 68px）列对不齐。改用 `display: grid` + `repeat(var(--segment-columns), minmax(0,1fr))`。

**坑：测试断言别手算位置数字**
写光标插入测试时两次算错（忘了尾随空格会移动光标）。改成断言 `value.slice(0, caret)`
与 `value.slice(caret)` 的边界，比手算数字可靠。

**坑：预览夹具不能编数据**
`test/preview.html` 里我编过 5 个思考档位，而真实目录最多 4 档
（`deepseek-flash`）→ 调样式时是照着假数据调的。已改成真实档位，并留了
`scripts/effortProbe.ts` 可随时核对真实档位数。

**坑：慢的不是"构建"，先量再改**
用户反馈"build 很慢"。实测分解后发现 `npm run build` 只要 0.66s，真正的瓶颈是
`npm test` 14.6s，而其中 **11.6s 单独来自 token-cleanup 一套断言**（其余 13 套各约 110ms）。
→ 规避：性能问题先做**分阶段计时**（`node scripts/bench.mjs`），别照着"感觉"优化。
   我一开始以为要动 esbuild 配置，实际 esbuild 根本不是瓶颈。

**坑（性能）：同步调用子进程会冻住扩展宿主**
`processRegistry` 原来整条链路用 `spawnSync`：判定「命令行是不是 dsh」要起 PowerShell，
Windows 上约 1.5s，而 JS 是单线程——这 1.5s 里扩展宿主**完全无响应**（启动时表现为界面迟滞）。
→ 已改成异步（`spawn` + 手写超时/输出上限），同步段只剩租约文件读写（微秒级）。
   `scanServers` / `cleanupResidualServers` 现在是 async，调用方必须 await。
→ 异步化带出一个新坑：两个并发调用会各起一次 PowerShell（异步本为不卡主线程，
   却可能起两倍解释器）→ 用 single-flight（共享在途 promise）解决。
→ 回归防线写在测试里：断言调用**同步段的耗时 < 250ms**（注入 1.5s 忙等验证过会失败），
   以及**并发扫描只起一次 PowerShell**（去掉 single-flight 验证过会变 2 次）。
   这类"不阻塞"的性质无法靠读代码保证，必须用耗时断言钉住。

**坑：Windows 上"逐个查进程"会付 N 次解释器启动成本**`processRegistry` 原来对每个孤儿 pid 起一次
`powershell -Command "(Get-CimInstance Win32_Process -Filter ...).CommandLine"`。
实测：单查一个 pid ≈1600ms，而**一次查全部进程**≈1800ms——代价几乎全在 PowerShell 启动上，
查询本身不要钱。于是 N 个孤儿 = N×1600ms。
→ 改法：`Get-CimInstance Win32_Process | Select-Object ProcessId,CommandLine | ConvertTo-Json`
一次取回，按 pid 建索引。`wmic` 已在新版 Windows 移除（ENOENT），不能用；
`pwsh` 比 `powershell.exe` 快约 300ms，所以优先 pwsh、失败退回。
→ 附带：这同时拖慢**扩展启动时的残留清理**（同步 spawnSync 会卡住扩展宿主），所以是产品与开发双赢。

**坑：缓存"能回答全部 pid"才可复用，否则会漏掉刚启动的进程**
给命令行快照加 TTL 缓存后，2c 场景立刻失败：进程是在上次快照**之后**才启动的，
缓存里没有它 → 被当成"查不到命令行"。修法是缓存只在 `pids.every(has)` 时复用，
否则重取。这类"缓存造成的假阴性"很容易被误读成"查询失败"。

**坑（安全）：三态判断写反了方向，会误杀进程**
`confirmed` 是三态：`true` 确认是 dsh / `false` 确认不是 / `undefined` 拿不到命令行。
原代码 `if (confirmed === false) 跳过`，于是 **undefined 落到下面被 taskkill 掉**——
与函数注释"拿不到命令行就不动进程"正好相反，而那恰恰是最无法排除"pid 已被回收"的情形。
→ 抽出纯函数 `isKillable()` 用 `=== true`，并直接单测三态。
   教训：**安全谓词要按"肯定证据"写（`=== true`），不要按"否定证据"写（`!== false`）**。

**坑：注入式回归验证必须先确认注入真的生效**
见上一条「`Set-Content -NoNewline`」。这次改用 `edit` 工具注入 → 跑 → `edit` 还原，
每条新断言都验证过"注入旧缺陷后确实失败"，才敢说它有效。

**坑：把用户的需求读成了 bug 报告，反向实现**用户说「思考完毕的鲸鱼显示为蓝色而不是灰色」——这是**要求变成蓝色**（「A 而不是 B」=
要 A）。我读成「鲸鱼是蓝色，这是个 bug」，于是让它变灰，交付时还自称「已修复」。
两次往返才纠正。
→ 规避：中文里「X 而不是 Y」几乎总是**期望 X**，不是「报告 X 有问题」。
   拿不准时交付前用一句话复述验收标准（如「结束后是蓝色、且不呼吸」）让用户确认。

**坑：同一语义的两个元素被差别对待（`prefers-reduced-motion` 名单漏项）**
`.dot-running` 与 `.icon-glow` 是同一类活性指示器，但减少动效的抑制名单里只列了前者。
用户机器 `MinAnimate = 0`（Windows 动画效果关闭）→ 表现为「鲸鱼在呼吸、圆点不动」，
看起来像任务卡死。
→ 规避：凡是「同类元素共享同一套视觉语义」的地方，断言要写成**待遇一致性**
   （`assert.strictEqual(hasA, hasB)`），而不是各写各的 `assert.ok`。
   这类 bug 单看任一元素的代码都完全正确。

**坑：小元素只靠 opacity 呼吸几乎看不出来**
7px 圆点 `opacity 0.7 ↔ 1` 在高分屏上难以察觉。改用 `box-shadow` 常驻光晕 +
动画呼吸：光晕跟着 opacity 一起明暗，且**不依赖动画**（被抑制时仍亮）。
→ 「亮着」用背景/阴影表达，「在呼吸」用动画表达，两者解耦后更健壮。

**坑：`Set-Content -NoNewline` 在 pwsh 工具里不存在**
注入 bug 做回归验证时用它写文件，报「找不到与参数名称 'NoNewline' 匹配的参数」，
**写盘失败但脚本继续** → 测试「通过」了，其实 bug 根本没注入，验证是假的。
→ 规避：注入式回归验证必须**先确认注入后的文件内容真的变了**（再跑测试），
   否则会把「没注入」误读成「防线无效/有效」。
   本项目里用 `edit` 工具注入 + 跑 + `edit` 还原更稳。

**坑：沙箱下构建/写家目录会失败（环境限制，非代码问题）**
- `pwsh` 后台作业里跑 `npm run build:scripts` 会 `spawn EPERM`
- `pwsh` 直接跑探针要写 `~/.dsh` 会 `EPERM: open ~/.dsh/profiles/web/cordis.yml`
- `pwsh` 里管道到 `Select-Object` / `Out-Null` 会报「不是内部或外部命令」（走了 cmd 语义）
→ 都用 **`build` 工具**跑（宿主直连、无沙箱）；`pwsh` 里避免管道到 cmdlet。

**坑：多次实测才能定论——cancel 与队列的关系**
只测一轮会得出矛盾结论（一次说队列会续跑、一次说不会）。6 轮重复后定论：
`cancel` **不会**让队列自动接续，且服务端是否顺带继续取决于中止落在轮循环哪一步，
客户端无法预判 → 所以实现成「摘空整条队列 → cancel → 等空闲 → 按原序重发」。

`controller.ts:1741` 注释引用「实测（`scripts/queueContinueProbe.ts`，两轮各 3 次）」——
**该脚本已在我早前的工作中删除**，仓库内不存在。ESC 设计的立论依据当前不可复现。

- **文件策略**：workspace-write，只能写 `D:\dev\dsh-chat`。`build/`、`dist/`、`Releases/`
  已在 `.gitignore`。
- **不要编造数据**：预览夹具与测试数据必须来自真实目录/真实事件
  （用 `scripts/effortProbe.ts`、`systemPromptProbe.ts`、`readRangeProbe.ts` 核对）。
- **`processRegistry` 是异步的**：`scanServers()` / `cleanupResidualServers()` 返回 Promise，
  新增调用点**必须 await**（同步段只有租约文件 IO；进程查询与 taskkill 都是 await 的）。
  不要为了"简单"改回 `spawnSync`——那会冻住扩展宿主约 1.5s。
- **协议事实**：`session/cancel` **不会**让队列自动接续；`steer` 在取消后不可用
  （要求 `status === 'running'`）；重发必须换新 `requestId`（旧 id 被当成重试不插入）。
- **审计报告的权威性**：以 `docs/audit-summary.md` 为准；两份分报告是子代理原始产出，
  覆盖面更广但**含未复核条目**（文件头已标注）。
