# 草稿（输入框内容）的生命周期与提交顺序契约

> 这份文档是「输入框里那串字归谁管、什么时候被清、什么时候还回去」的口径。动
> `Controller.send` / `commitDraft` / `appendDraft`、或改界面「发送」那条链路之前先读这一份。
> 2026-09-23 立：用户报的「消息发出后输入框先清空、又闪回一下、再消失」就是违反了第三节的顺序契约。

## 一、谁拥有草稿

- **权威表在宿主**：`ChatController.drafts`（内存 Map）。界面只持有**乐观镜像**（`AppState.draft`），
  改完立刻渲染、不等往返。
- **两个键**：还没有会话的窗口按 `viewId` 存，绑定会话之后按会话 id 存（`keyForView`）。
  绑定与退回空态各有一条迁移——`bindViewToSession`（窗口键 → 会话键）、`detachView`（会话键 → 窗口键）。
  两处的判据都是「值不是 `undefined`」：**空串也是草稿**，提交完立刻绑定会话时迁的就是这份空的。
- **整份状态快照里的 `draft` 读的也是这张表**（`snapshotFor`），所以宿主的表就是
  「界面重载 / 切会话 / 建会话之后看到什么」。

## 二、写点清单

| 时机 | 入口 | 动作 |
|---|---|---|
| 打字、补全选中、引用插入 | 界面 `writeDraft` | 两次写：本地 `ui/setDraft` + `setDraft` 帧（宿主持久化） |
| 按下发送 / 提交命令 | `Controller.send` 顶上的 `commitDraft` | 清空宿主表 + 推 `draft: ""`（**唯一入口**） |
| 没真的发出去 | `appendDraft` | 用户取消目录选择、拼不出内容块、`prompt` 抛错、队列重发失败 |
| 新建对话（`+`） | `detachView` + 整份快照 | 草稿跟着**窗口**走，不因为退回空态而丢 |
| 队列「重新编辑」 | `editQueuedMessage` | 按原文回填（已有草稿时追加，不覆盖） |
| 建会话 / 切会话 / 窗口就绪 | `snapshotFor` 的整份快照 | 带着当前草稿 |

## 三、顺序契约（坑点）

界面在按下发送那一刻就清空了自己的镜像。由此推出两条不变量，**两条都落在宿主**，
因为只有宿主知道「这条到底发出去了没有」：

1. **提交即清空必须早于任何可能推整份快照的 await。**
   空态第一次发消息时 `send` → `ensureSession` → `createSession`，而 `createSession` 在绑定窗口后
   会推一份整份快照（会话页要从空态切换过来，这一帧不能省）。快照里的 `draft` 读宿主的表——
   清空晚于它一步，那一帧就把刚发出去的正文塞回输入框。
2. **没真的发出去，就必须把草稿还回去。**
   「宿主收到 `send` 帧」等价于「界面里已经是空的」，所以没提交成功的每条路径（拿不到会话、
   拼不出内容块、`prompt` 抛错、连不上后台）都要用 `appendDraft` 把正文推回输入框，
   而不是静默 `return`——静默返回等于吞掉用户那句话。

## 四、界面为什么不自己补一帧清空

界面只做乐观清空，**不**额外补发 `setDraft ""` 帧：那等于把顺序押在两条 postMessage 的到达
顺序上，而宿主仍可能在处理 `send` 之前推出快照（不变量落在没人守的那一侧）。
宿主侧的 `commitDraft` 是唯一入口，两处重复的清空（斜杠分支、提交补丁里的 `draft: ""`）
已经收进它。
