## 提交：queue / steer / 加速手势

### 1.1 提交模式解析 —— 已修

- **官方口径（判定依据）**：`resolveSubmitMode(preferred, running, gesture,
  steeringAvailable)`——未在运行、或本会话不支持插话（非子代理，或 continuable 子代理）
  → 一律 `queue`；`enter` 手势 → 取首选值；加速手势 → 取首选的相反值。首选值默认
  `queue`，由 `ui-conversation.busyEnter` 用户设置覆盖；按钮文案会预告下一步行为
  （`input.send.steer` / `input.send.queue`）。
- **审计当时的扩展问题**：两处调用点写死 `"queue"`、从不读 `ui-conversation`——设置
  面板里改 `busyEnter` 会「显示已保存、行为不变」（静默失效）。
- **判定：已修（2026-09-14）**。现行做法：`resolveSubmitMode` 逐字移植官方；冷启动也
  读设置；`running` 判定移到乐观置位之前。

### 1.2 加速手势 —— 已修；「整队插话」未做

- **官方口径**：加速手势（Ctrl/Cmd+Enter）有独立语义——空草稿且可整队插话时，加速
  Enter = 把整个队列插话发出（`steerQueue`）；否则取与首选相反的提交模式。
- **现行做法（已修，2026-09-14）**：Cmd/Ctrl+Enter 走 `gesture:"accelerated"`，运行中
  取 `busyEnter` 的相反值；忽略 `event.repeat`。队列行插话已做（`session/updateQueue`
  的 `{kind:'steer'}`）。
- **仍未做**：空草稿 + 加速手势 → 整队插话（官方 `steerQueue` 的对应物）。
- **无法确认**：VS Code webview 是否会先吞掉某些组合键（未实测）。

### 1.3 客户端自铸 `requestId` —— 一致

官方与扩展都是客户端自铸 UUID（契约写明 Client-minted，重复提交同一 id 幂等）；该 id
落到 durable `user/message` 的 `source.rpcId` 并作为队列项 `rpcId` 回传。扩展同样上报
`clientTimeZone`。无差异。

## 队列与重新编辑

队列来源（2026-09-18 起）：服务端已删除 `session/control` 的 `SessionQueuedItem` 帧通道，
队列改由 **`inbox` 投影**（`next-turn` / `next-step`）承载。扩展曾只读旧帧，表现为待发
列表整体消失（用户报过）；现已**双读**新投影与旧帧，折算见 `src/dsh/queueView.ts`。
「停止 / 取消与队列」的语义结论不受此影响（见下文停止一节）。

### 2.1 队列行的「重新编辑」—— 不一致（回填链路已修，2026-10-10）

- **官方口径**：编辑在队列行内进行，提交服务端 `action{kind:'edit'}`（只收纯文本），
  服务端**原地替换**（队列项 id、位置不变）；编辑原文来自权威队列行自身，无文本的行
  直接禁用编辑；保存后行内附件被服务端丢弃。官方不碰输入框草稿。
- **扩展现状**：仍是 `remove` + 本地回填——先摘除队列项，成功后把文本**追加**进当前
  草稿、把原附件塞回芯片；客户端只实现了 `{kind:'remove'}`，没有 `kind:'edit'`。
- **回填链路已修（2026-10-10）**：现在是「**先抓好、先把附件预备齐，再摘**」
  （`editQueuedMessage`）。原文 / 附件 / 草稿键一律在 `await` 之前抓好：此前是等摘除 RPC
  回来再读 `queueOrigin`，而摘除生效后服务端立刻重推队列（`inbox` 投影 / 旧 `queue` 帧），
  那次重推经 `syncQueue` 整表重建来源索引——被摘掉的那一项已不在表里，于是**带附件的
  排队消息取回重编时附件全丢**（只回填正文并弹丢失警告）。跟随流与控制流分居两条 socket，
  回显**允许**先于 RPC 的 resolve 到达；该排列已由离线回路复现（实际发生率未测，回归只
  断言「这个排列成立时结果必须正确」）。
  **附件还原不了的这一条根本不摘**：还原计划与图片字节（durable 句柄经
  `session/attachment` 换回）全部先算出来，只要有一枚还原不了就**保持队列原样**
  （队列项、来源索引、原草稿、原附件都不动）并提示「部分附件无法还原，消息已保留在
  队列中」（`@queueAttachmentsLost`）——不做「摘了再只回填一部分」。摘除成功之后才回填。
  同一处还修了⑤：`await` 期间切会话不再把内容写进新会话的输入框（写回原会话的草稿，
  切回去就能看到；提示同样按会话投递，不越会话），remove 失败时草稿与来源索引都不动
  （可重试）。
  回归：`scripts/queueRestore.test.ts`（真 `ChatController` + vscode stub，含回显时序的
  差分对照、完全可还原的对照、三类「整条不动」的负面场景）。
- **用户可见差异（未修部分）**：①位置——官方原地替换，扩展重发后排到队尾；②草稿污染
  ——扩展把内容拼进用户已有草稿（只按肯定身份去重：同 id / 同上传回执 / 同 durable
  句柄 / 图片同字节）；③附件命运相反——官方丢附件、扩展在**能完整还原**时才取回
  （还原不了就留在队列里，不静默丢）；④官方是行内单行编辑、不能加附件，扩展等价于
  「取回重写」。

### 2.2 编辑「原文」的本地缓存 —— 不一致（重载边界已定，2026-10-10）

- **官方口径**：不需要本地缓存，编辑原文就是权威队列行的 `row.text`。
- **扩展现状**：原文来自本地提交记录（TTL 30 分钟、上限 50 条，超期 / 超量淘汰）；
  淘汰后回退到线上正文（内联改造前正文里塞着文件全文，直接回显「很吓人」——扩展注释
  自认）。
- **重载 / 淘汰后的附件边界**：本地记录不在时退回队列内容的**内容块**，可还原性由线
  格式决定——图片块（durable `attachment{attachmentId,mediaType,bytes,name}`）能用
  `session/attachment` 换回字节，与回放同一条通道，所以**纯图片的那条仍能完整取回**；
  文件块只有 `attachmentId`（字节 sha256），**没有上传回执**，而发送只认回执——伪造
  一枚发不出去的文件芯片比不还原更糟，所以只要碰到这种块（或图片字节取不到）就**不
  取回**，消息原样留在队列里并提示。
- **后果（未修部分）**：长会话（>50 条提交）或超 30 分钟后，正文退化为线上正文；带
  文件的排队消息**不能**再取回重编（需先备好正文和完整附件，再取消旧消息并重新发送）。
  官方无此退化。（§3.1 内联口径已改，正文膨胀一项不再成立。）

### 2.3 `steering` 行被当普通排队行 —— 不一致（未修）

- **官方口径**：队列面板只取 `placement === "queued"`；`steering` 是「已插进当前轮、
  待被 loop 取用」的在途项，在转写里以 steering 节点呈现。行级 / 整队插话走
  `{kind:'steer'}`，只在项仍在 `next-turn` 且 agent 运行中时可用，否则服务端报
  `session/steer-unavailable`。
- **扩展现状**：`queueView` 只滤掉 `context`，`steering` 行被当「排队中（尚未发送）」
  展示，并可编辑 / 取消。
- **后果**：在途插话显示成未发送；「编辑」它 = 摘除 + 回填，插话内容被吞；停止流程把
  steering 行按 `mode:"queue"` 重发，插话语义被降级成排队。

## 上下文与附件

### 3.1 文件内容的线上表示 —— 已对齐

- **官方口径**：文件只有三条通道、全部不内联正文——①`@` 路径引用（模型侧形态就是
  `@path`，配套系统提示让模型自己去 read）；②文件上传回执（原始字节上传、提交只发
  `receiptId`；服务端逐字节保存、存储无准入限制；模型看到的是「只读副本已存于某路径」
  的句柄文本）；③会话引用 `@[label](dsh-session:…)`。
- **现行做法（已对齐，2026-09-14 起细化）**：`@` 变成正文里的 `@path` token（不再生成
  附件栏芯片），上传只留给「模型可直接读的文本」。
- **落盘的会话引用按原始 token 下发（2026-10-10）**：服务端只替换**给模型的那一份**
  副本（`prepareDirectMessages`），durable 事件里仍是 `@[标题](dsh-session:…)`。宿主
  从前把它折成可读的 `@标题` 再交给界面，会话 id 因此到不了界面、用户**已经发出**的引用
  点不开——现在原样下发（`adapter.ts` 的 `user/message` 分支），界面侧
  `webview/mentionLinks.ts` 切成可点的行内链接：显示仍是 `@标题`、复制走可读文本
  （`readableMentionText`）、轮次大纲的提问预览同样先还原。轨迹视图
  （`dsh/trajectory.ts` 的 `user/message`）没有链接能力，只做同一条显示还原。
- **审计当时的差异要点（设计取舍记录）**：全量内联显著抬高 token 与上下文压力；二进制
  / 超大文件拿不到正文；`@` 的模型侧语义（可追踪的工作区路径引用）被抹掉。

### 3.2 内容块顺序 —— 不一致（低影响）

- **官方口径**：附件在前、文本在后。
- **扩展现状**：文本（含上下文文本块）在前、图片在后。
- **影响**：线格式差异；对多数多模态模型影响很小，做消息对比 / 审计时会不一样。

### 3.3 仅附件不能发送 —— 不一致（未修）

- **官方口径**：空判定是「草稿空且无附件」——只挂附件时 Send 可用，提交机还有专门的
  纯附件提交事件。
- **扩展现状**：发送可用性要求草稿非空——只挂图时按钮禁用、Enter 也被挡；而宿主侧
  其实能发（有附件块就继续装配），属**纯 UI 限制**。
- **影响**：想只发一张图 / 一个文件的用户做不到（除非随便打一个字）。

### 3.4 拖放 / 粘贴文件 —— 已修（2026-09-21 两条路落地）

- **官方口径**：拖放与粘贴都进 `intakeFiles`（自带图片数量 / 大小校验），有整屏
  `DropOverlay`。
- **现行做法**：落点 `src/webview/attachIntake.ts`（App 的 `usePageFileDrop` /
  `usePagePaste` 各挂一个 window 监听），拖放与粘贴共用一条字节通道；路径 / 字节两条
  平行通道已合成一条（`planIntake` + `ingestAttachments`）——字节通道附件曾因缺 `path`
  被发送装配漏掉、连提示也不发，已修（装配改看上传回执）。
- **关键机制（防再踩）**：VS Code 桌面 webview 里 `Ctrl+C/V/X` 被 pre 脚本
  `preventDefault` 后由宿主补发 `execCommand("paste")`，webview 文档里因此会真的触发
  `paste` 事件——**不要自己挂 keydown 抢 Ctrl+V**，那会在宿主之前吃掉按键，反而让它
  不再补发。
- **剪贴板实测（2026-09-21）**：webview 侧拿不到路径——`text/uri-list` 为空串、
  `File.path` 自 Electron 32 起移除，目录的字节也读不出来。真路径只能由宿主读系统
  剪贴板：`src/dsh/clipboardPaths.ts`（Windows 用 `powershell.exe -Sta` + WinForms
  `GetFileDropList`，5 秒超时；非 Windows 或读不到返回空）。按类别分流：目录 →
  `@目录/` 引用（用户明确「粘贴文件夹不该变成附件」）；文件 → 附件通道（图片内容块 /
  其余上传）；取不到路径才退回字节通道（截图那类）。
- **拖放限制**：拖放拿不到 OS 路径（webview pre 脚本不转发、Electron 32+ 移除
  `File.path`），**拖放文件夹作废**（只剩提示），拖放文件不受影响。
- **仍未对齐**：官方有图片整批预检（数量 / 总量 / 像素）与上传进度，扩展没有；字节
  通道受单文件 8 MB 限制（`ATTACH_BYTES_LIMIT`）；浮层只有拖放有；路径读取仅 Windows。
  完整设计见 `docs/design-attachments.md`。

## 选区上下文

### 4.1 选区内联 —— 不一致（扩展独有能力）

- **官方口径**：提交内容、命令附件、结构化引用的联合类型里都没有 selection / quote
  形态；官方的 `selection` 只表示编辑器内的光标 / 选区区间；引用工作区内容的官方方式
  就是 `@` 路径（模型自己 read）。
- **扩展现状**：编辑器右键 `dshChat.addSelection` 把选区做成 `kind:"selection"` 附件，
  发送时内联为「来自某文件的选中代码」代码块。
- **判定**：与官方不一致是确定的；是否算缺陷取决于产品取向——对「只发一小段代码」的
  用户更省 token，代价是选区快照无行号、无路径 token，发送前内容变化则模型看到过期
  快照且无任何提示。

## 斜杠命令

### 5.1 手打 `/xxx` 走 prompt 而非 `commands/execute` —— 不一致（重大，未修）

- **官方口径**：`/` 开头的草稿进入 adjudication，由命令源认领后走 `commands/execute`
  （Host 侧明确「不进模型」）；没有任何 source 认领才落到默认 sink（`session/prompt`）。
  Host 不解析聊天正文里的 `/命令`。命令提交可带草稿附件（如 `/plan` 声明
  `input.attachments`），命令运行渲染成持久流程节点（`command/run` / `command/done`）。
- **扩展现状**：`commands/execute` 只用于权限胶囊（`/permission`）；用户手打的 `/xxx`
  走普通发送（发送路径无 `/` 分支），命令目录只用于补全；`/plan` 进 / 出都是拼进消息
  正文。
- **后果**：`/compact`、`/export`、`/goal` 等全部变成给模型的一句普通文本；`/plan` 不会
  真正置位 Host 侧 plan 状态（plan 激活只发生在命令 handler 里），扩展的 plan 胶囊几乎
  不会变 true；且扩展用 `"/plan"` 表示**退出**、官方语义里 `"/plan"` 是**进入**——即使
  将来接上命令通道，这个方向也是反的。
- **主线实测补充**：`scripts/planCommandProbe.ts` 用真实服务器证实「`/plan` 走 prompt
  正文无效、必须走 `commands/execute`」（见 `audit-summary.md`）。

### 5.2 `commands/execute` 参数形状 —— 一致；`images` 回退是死代码

- **官方口径**：参数为 `agentId` / `line` / `submittedAttachments`（图片与 staged file
  receipts，按提交顺序；纯命令调用传空数组）。
- **扩展现状**：先试 `submittedAttachments`，命中 `gateway/arguments-invalid` 才回退
  `images`。全安装树里 `images` 只出现在 fixture 测试替身，无生产端接受该名字——回退
  分支对当前版本应属死代码（保留无害）。
- **残留差异**：扩展永远传空数组，官方把草稿附件一起提交——「带图片执行 `/plan`」官方
  成立、扩展不可能（既不走命令通道也不做上传）。

## 停止 / 取消与队列

### 6.1 停止语义 —— 不一致（语义结论保留）

- **官方口径（契约）**：`cancel` 只中止当前轮——「待办的排队工作保留，并在 Host 到达
  取消静默后按 FIFO 续跑」；Host 实现带 `keepInbox: true`；官方 UI 的停止就是这一个
  调用，不碰队列。与停止相关的队列操作是显式的（单行插话 / 整队插话）；官方没有
  「停止后自动把队列第一条发出去」的语义。
- **扩展口径（实测结论，写在 `stopRunning` 的注释里）**：①只 `cancel` **不会**让队列
  自动接续；②服务端是否顺带继续取决于中止时刻落在哪一步。另有一条顺序依据：若不先
  摘空，中止后立刻提交的新消息会被「abort 后唤醒」锁存进 `next-turn`，排在仍留在队列
  里的消息之后（顺序倒置）。
- **现行做法（stopRunning 的设计依据）**：先把整条队列摘空（含 steering 行）→
  `cancel` → 等空闲（上限 8 秒）→ 按原顺序逐条以 `mode:"queue"` 重发（每条自铸新
  requestId）。中途 remove 失败会把已摘的重新排回（也是重发，会换 requestId 与顺序）；
  摘空之后、重发之前退出 / 重载，这些只存在于内存里的消息会彻底丢；队列空且拿不到可
  重发内容时弹队列内容丢失警告。
- **分歧（本审计最需实测确认的点）**：契约说会续跑、扩展注释说不会，二者必有一方在
  当前版本上不符合事实——见「无法确认」第 1 条。
- **用户感受**：扩展按停止 = 「停止 + 立刻发出队首」；官方 = 本轮结束后队列由 Host
  自然消费。在途插话被重发成排队（降级）。

## 无法确认 / 证据缺口

1. **cancel 后队列是否自动 FIFO 续跑**：官方契约说会；扩展注释说不会并提到探针脚本

   「先摘空」流程，没有验证「只 cancel」。无运行时证据。

3. **剪贴板里的文件（CF_HDROP）经 `execCommand("paste")` 会不会投递成

6. **`Attachment.kind === "context"` 的入口**：发送装配只处理 `selection` 与 `file`，

   无法确认该分支是否有实际入口。

## 排序：真正影响用户的差异 vs 无害选择

**A. 真正影响用户（已修的标注）**

1. `busyEnter` 被忽略 + 加速手势无区分（1.1 / 1.2）——**已修**；剩「空草稿 + 加速 =
   整队插话」未做。
2. 手打斜杠命令不执行（5.1）——未修；`/plan` 连带计划模式不置位、退出按钮发的是
   「进入」指令。
3. 文件上下文全量内联（3.1）——**已对齐**（`@path` token）。
4. 停止语义与官方相反（6.1）——未修；摘空 + cancel + 重发，多 RPC、8 秒等待、有损
   窗口、插话降级；其赖以成立的前提（cancel 不续跑）在本仓库无可复现证据。
5. 队列编辑的落点与官方不同（2.1–2.3）——未修；位置变队尾、草稿被拼、缓存淘汰退化、
   steering 降级。其中「取回重编丢附件」与「切会话写错草稿」两条回填缺陷**已修**
   （2026-10-10，见 2.1/2.2）。
6. 「看起来支持、其实无声失败」类（3.3 / 3.4）——拖放 / 粘贴**已修**；仅附件不能发
   **仍待处理**。

**B. 有差异但影响很小 / 基本无害**

7. 内容块顺序（3.2）。
8. `images` 回退分支（5.2）——死代码，无害。
9. `requestId` 自铸、`clientTimeZone` 上报（1.3）——与官方一致。
10. `/permission` 走 `commands/execute`——与官方同类操作语义一致、参数名正确。

**C. 扩展独有（官方无对应物，不算错误，但属不一致）**

11. 「选区」内联（4.1）。
12. `notInlinedNote`、`@attachmentNotInlined` 等自造提示——官方不做内联判定，故无
    对应概念。
